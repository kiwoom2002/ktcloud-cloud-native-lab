## 1. Docker — 실습 13개 · 미션 2개

**핵심: 앱과 실행 환경을 이미지 하나로 묶어, 어느 서버에서든 같은 방식으로 실행·배포할 수 있게 만드는 법을 배웠습니다.**

| 주제 | 실습에서 한 일 |
|---|---|
| 네트워크·셸 기초 | IP·DNS·포트·HTTP 상태 코드를 `curl` 등으로 확인, 파이프(`\|`)·리다이렉션·환경변수·종료 코드(`echo $?`), nano 편집 |
| 컨테이너 전과 후 비교 | VM에 Node.js를 직접 설치해 앱 실행 → 컨테이너로 Node 18·22를 한 VM에서 동시에 실행해 환경 격리 확인 |
| 컨테이너 운영 | nginx 컨테이너 실행·포트 매핑(`-p`)·로그 확인, 중지·재시작·`exec`·삭제, 자주 나는 오류 3가지 재현과 해결 |
| 이미지 빌드 | Dockerfile 작성, **레이어 캐시**를 살리도록 `COPY package*.json` → `npm ci` → `COPY .` 순서로 정리해 빌드 시간 단축, `.dockerignore` |
| 레지스트리 | Docker Hub에 태그 규칙(`아이디/이름:태그`)으로 push / 다른 VM에서 pull |
| 데이터 영속성 | 이름 있는 **볼륨**으로 컨테이너를 지워도 데이터 유지, **바인드 마운트**로 재빌드 없이 코드 반영 |
| 컨테이너 네트워크 | 기본 브리지에서는 이름 해석이 안 되는 것 확인 → **사용자 정의 네트워크**로 API ↔ PostgreSQL을 컨테이너 이름으로 연결 |
| Docker Compose | web(nginx) · api(Express) · db(PostgreSQL) **3티어**를 `compose.yaml` 하나로 `up` / `down` |

- **미션 1. 내 앱 이미지 만들기** — 참고 없이 Dockerfile을 처음부터 작성하고, 기능을 더한 v2를 v1과 나란히 실행
- **미션 2. Compose로 Online Boutique 조립** — 언어가 다른 마이크로서비스 5~6개를 Compose로 엮어 실행, 서비스 간 의존 관계와 로그 읽는 법

## 2. Kubernetes — 실습 12개 · 미션 2개

**핵심: 컨테이너를 선언형 YAML로 배포하고, 자가 복구·롤링 업데이트·서비스 디스커버리·자원 관리를 쿠버네티스에 맡기는 법을 배웠습니다.**

| 주제 | 실습에서 한 일 |
|---|---|
| 클러스터·kubectl | kind로 클러스터 생성(노드가 Docker 컨테이너임을 확인), `get` · `describe` · `top` · `explain`, 네임스페이스 |
| Pod·워크로드 | `kind load`로 이미지 주입 후 Pod 실행, 멀티 컨테이너 Pod, **Deployment**(삭제해도 재생성·스케일), DaemonSet·Job |
| 배포 전략 | v1 → v2 **롤링 업데이트**, `rollout undo` **롤백**, 없는 이미지로 바꿔도 기존 Pod가 서비스를 유지하는 것 확인 |
| 네트워킹 | **Service**(ClusterIP·NodePort)로 고정 이름 제공, `port-forward`, **Ingress**(Traefik)로 `hello.localhost` · `todo.localhost` 호스트 기반 라우팅 |
| 설정 분리 | 설정은 **ConfigMap**, DB 비밀번호는 **Secret** — 이미지·YAML 밖에 두는 이유를 직접 비교 |
| 스토리지 | PostgreSQL 데이터를 **PVC**에 붙여 Pod를 지워도 데이터 유지 |
| 헬스 체크 | **readinessProbe**(준비 안 된 Pod로 트래픽 차단), **livenessProbe**(멈춘 앱 자동 재시작) |
| 자원 관리 | **requests / limits**, `Pending`·`OOMKilled` 재현, **HPA**로 부하에 따른 자동 확장 |
| 패키지 관리 | **Helm** 차트로 Online Boutique(서비스 11개) 설치 · 값 변경 업그레이드 · 롤백 |

- **미션 1. Online Boutique를 쿠버네티스로 옮기기** — Compose 서비스 하나 = Deployment + Service로 변환, 서비스 5개 마이그레이션
- **미션 2. 고장 난 Online Boutique 고치기** — 숨은 장애 6개를 `get → describe → logs`, Service 엔드포인트 확인 순서로 **트러블슈팅**

## 3. 클라우드 보안 — 실습 10개 · 미션 2개

**핵심: 이미지 · 워크로드 · 클러스터 · 공급망 단계마다 보안 통제를 걸어, 기본값의 빈틈을 코드와 정책으로 막는 법을 배웠습니다.**

| 주제 | 실습에서 한 일 |
|---|---|
| 위협 확인 | 기본값 그대로일 때의 빈틈 3개(root 실행, 네임스페이스 간 열린 네트워크, 자동 마운트된 API 토큰)를 확인하고, 두 빈틈을 이어 다른 네임스페이스에서 데이터를 읽고 지우는 것까지 재현 |
| 이미지 스캔 | **Trivy**로 `todo-api` 이미지 취약점 스캔, 취약점이 코드가 아닌 **베이스 이미지**에서 온 것 확인, 베이스 이미지별 비교, `--exit-code`로 실패 처리 |
| 이미지 하드닝 | **non-root**(`USER 1000`)·불필요한 npm 제거한 `todo-api:safe` 빌드, `trivy config`로 설정 점검 |
| SecurityContext | `runAsNonRoot`, `readOnlyRootFilesystem`, capability 제거 등을 하나씩 켜고 실패 메시지 해석 |
| Secret 관리 | Secret은 base64일 뿐 암호화가 아님을 확인, 환경변수 대신 **파일 마운트**(권한 제한), `automountServiceAccountToken: false` |
| RBAC | 넓은 권한(`edit`)의 위험 확인 → 파드 **읽기 전용** ServiceAccount 생성, `kubectl auth can-i`와 실제 토큰으로 허용/거부 검증 (최소 권한 원칙) |
| NetworkPolicy | **default deny** 후 `web → api → db` 두 경로만 허용 |
| Pod Security Admission | 네임스페이스 라벨 하나로 `restricted` 기준 미달 Pod를 `Forbidden` 처리, `warn` 모드로 사전 점검 |
| 정책 엔진 | **Kyverno** `ValidatingPolicy`로 "태그 없음·latest 금지" 규칙 작성 → admission 단계에서 거부 |
| 공급망 보안 | Trivy로 **SBOM**(CycloneDX/SPDX) 생성 후 SBOM만으로 취약점 탐지, 로컬 레지스트리에 올린 이미지를 **cosign**으로 서명·검증, 같은 태그 덮어쓰기 공격 탐지 |

- **미션 1. 취약한 memo-api 고치기** — 앱 코드(Python)는 그대로 두고 Dockerfile과 매니페스트만 고쳐 보안 점검 기준 통과
- **미션 2. shop 네임스페이스 격리** — 서비스 11개에 `restricted` PSA와 NetworkPolicy를 적용하면서도 쇼핑몰 기능(홈·장바구니)은 정상 동작하도록 조정

## 4. CI/CD — 실습 7개 · 미션 2개

**핵심: push 한 번으로 테스트 → 이미지 빌드 → 보안 스캔 → 레지스트리 업로드 → GitOps 배포까지 자동화하고, 배포와 롤백을 Git 커밋 하나로 다루는 법을 배웠습니다.**

| 주제 | 실습에서 한 일 |
|---|---|
| Git 협업 | 커밋·push, 브랜치 → **PR** → main 병합 → pull |
| GitHub Actions | `on.push.paths` 필터, `npm ci && npm test` → `docker/build-push-action`으로 **GHCR** 업로드, 태그는 `:<커밋 SHA>`(배포용)와 `:main`, `GITHUB_TOKEN`·`permissions: packages: write`로 비밀번호 없는 인증 |
| 품질 게이트 | 테스트를 일부러 깨뜨려 이미지가 올라가지 않는 것 확인, `git revert`로 이력을 남기며 되돌리기 |
| 보안 게이트 | 워크플로를 `test` / `scan` / `push` job으로 분리, 고칠 수 있는 **CRITICAL** 취약점이 있으면 push 차단, PR에서는 검사만 하고 업로드는 main에서만 |
| Jenkins | Jenkins를 컨테이너로 띄우고(JCasC `casc.yaml`), `Jenkinsfile` 스테이지: 테스트 → 빌드 → 스캔 → 올리기 → **dev 매니페스트 태그 갱신 커밋**, Credentials로 토큰 관리 |
| Argo CD (GitOps) | Kustomize `deploy/overlays/dev`를 `todo-dev`에 배포하는 Application 작성, 손으로 바꾼 리소스가 Git 상태로 **자동 복구(self-heal)** 되는 것 확인 |
| 배포·롤백 | 코드 한 줄 push → Jenkins가 `jenkins-N` 이미지 빌드·태그 커밋 → Argo CD 배포, 문제 시 매니페스트 커밋 `git revert`로 롤백 |

- **미션 1. todo-web 파이프라인** — web(nginx)용 파이프라인에 `nginx -t` 설정 검사를 테스트로 넣고 Trivy 게이트 적용
- **미션 2. push 한 번으로 dev 배포, prod는 승인** — dev는 자동 배포, prod(`todo-prod`)는 dev에서 검증된 태그만 **PR 승인**으로 반영 후 Sync, 문제 시 Git으로 되돌리기 (환경별 승격 전략)

## 5. 서비스 메시 — 실습 6개 · 미션 1개

**핵심: 앱 코드를 바꾸지 않고 사이드카 프록시로 서비스 간 암호화·인가·트래픽 분할·장애 대응을 거는 법을 배웠습니다.**

| 주제 | 실습에서 한 일 |
|---|---|
| Linkerd | 노드 3개 클러스터에 control plane과 viz 설치, todo에 프록시 주입 → 코드 변경 없이 성공률·RPS·지연 확인, **mTLS** 자동 적용 |
| 신원 기반 인가 | api에 전용 ServiceAccount를 주고 "api 인증서를 가진 연결만 db 허용" 정책 → 라벨을 위장한 Pod도 차단 (NetworkPolicy의 IP/라벨 기반과 비교) |
| Istio 카나리 | todo-api v1·v2를 함께 띄우고 DestinationRule(subset) + VirtualService로 **v1 90% / v2 10%**, 헤더 `x-canary: true`는 항상 v2 |
| 복원력 | 장애 주입(지연·오류)으로 문제 상황 재현 → VirtualService로 **타임아웃**과 **재시도** 적용 |
| 관측 | Online Boutique 전체에 Istio 주입, **Kiali**로 서비스 관계도·mTLS 확인, 지표가 `istio_requests_total`에서 오는 것을 Prometheus로 확인 |

- **미션. 고장 난 메시 고치기** — 메시 설정에 숨은 장애 4개를 응답 코드 → 오류 문구 → Kiali → `istioctl analyze` → 규칙 목록 순서로 찾아 수정

## 6. 모니터링 — 실습 8개 · 미션 2개

**핵심: 지표(Prometheus) · 로그(Loki) · 트레이스(Tempo)를 함께 써서 "무엇이 → 언제부터 → 어디서" 나빠졌는지 좁혀 가고, 경보와 SLO로 장애를 먼저 알아차리는 법을 배웠습니다.**

| 주제 | 실습에서 한 일 |
|---|---|
| 수집 스택 | Helm으로 **kube-prometheus-stack**(Prometheus · Grafana · Alertmanager) 설치, Targets · Query · Alerts 확인 |
| 대시보드 | Grafana 기본 대시보드로 노드·파드 확인, 패널 뒤 PromQL 읽기 |
| PromQL | 라벨 필터, `rate`, `sum by`, `histogram_quantile`(p95 지연), `topk` |
| 앱 계측 | todo-api 코드에 지표를 직접 달아 `/metrics` 노출 → **ServiceMonitor**로 수집, 경로별 지표 확인 |
| 대시보드 구축 | 요청 수 · p95 처리 시간 · 5xx 비율 패널(`or vector(0)`로 No data 처리), DB 장애 시 변화 확인, JSON으로 내보내기 |
| 로그 | **Alloy**로 수집 · **Loki**에 저장, **LogQL**로 검색, JSON 로그 필드 필터링, Pod 삭제 후에도 로그 보존 확인 |
| 분산 트레이싱 | **Tempo** 설치, Istio 사이드카 스팬을 OTLP로 전송, 요청 하나가 거친 서비스·구간별 소요 시간 분석, 끊긴 트레이스 원인 확인 |
| 경보·SLO | "frontend 5xx 비율 1분간 10% 초과" 경보 규칙 → Alertmanager 라우팅 → 수신 확인, **SLO 99.5%** 기준 SLI·**오류 예산 소진 속도(burn rate)** 기록 규칙 작성 |

- **미션 1. shop 골든 시그널 대시보드** — 앱이 지표를 내지 않는 서비스 11개를 Istio 사이드카 지표로 서비스별 트래픽·오류·지연 대시보드 구성
- **미션 2. 장애 찾기 — 지표 · 로그 · 트레이스** — 설정을 뒤지지 않고 관측 도구만으로 원인을 좁혀 찾고, 되돌린 뒤 **장애 보고서** 작성
